# Spring Boot LLM Integration — Code Review Checklist

Use this checklist to review a Java Spring Boot codebase that integrates with an LLM provider (OpenAI, Gemini, or via Spring AI). Check off items as they're verified; flag anything unchecked as a review comment.

---

## 1. LLM Integration Setup (OpenAI / Gemini)

- [ ] **Dependency choice is intentional** — using Spring AI starters (`spring-ai-openai-spring-boot-starter`, `spring-ai-vertex-ai-gemini-spring-boot-starter`) or a well-maintained SDK, not a hand-rolled HTTP client unless there's a documented reason.
- [ ] **API keys / credentials are externalized** — pulled from environment variables, a secrets manager, or `application.yml` placeholders (`${OPENAI_API_KEY}`), never hardcoded or committed.
- [ ] **Separate configuration per environment** — dev/staging/prod use different keys, model names, and rate limits via Spring profiles.
- [ ] **Model name/version is configurable**, not hardcoded in business logic (e.g. `spring.ai.openai.chat.options.model` in properties, not a string literal in a service class).
- [ ] **Timeouts are explicitly set** for the HTTP client (connect, read, write) — no reliance on library defaults that may hang indefinitely.
- [ ] **Retry policy exists** for transient failures (429, 5xx) with exponential backoff, and is bounded (max attempts / max duration).
- [ ] **Circuit breaker or fallback** is in place (e.g. Resilience4j) so LLM outages degrade gracefully instead of cascading failures.
- [ ] **Cost/token controls** — `max_tokens` (or equivalent) is set explicitly rather than left unbounded.
- [ ] **API version pinning** — Gemini/OpenAI API version or SDK version is pinned, not left on "latest," to avoid silent breaking changes.

---

## 2. Best Practices for Calling the Chat Client

- [ ] **Single, injectable abstraction** — a `ChatClient` (Spring AI) or thin wrapper service is injected via constructor injection, not instantiated ad hoc inside methods.
- [ ] **No client instantiation per request** — the chat client / underlying HTTP client is a singleton bean, reused across calls (avoids connection overhead and resource leaks).
- [ ] **Business logic is decoupled from the LLM client** — a service layer (e.g. `LlmService`, `SummarizationService`) wraps the raw client so controllers/domain code never call the SDK directly.
- [ ] **Synchronous vs. async/streaming is a deliberate choice** — if the UI needs streaming responses, `Flux<String>` / SSE is used correctly; if not, blocking calls are documented and bounded by timeouts.
- [ ] **Thread pool sizing considered** — LLM calls (I/O-bound, often slow) run on a dedicated executor/`TaskExecutor`, not blocking the default request-handling threads under load.
- [ ] **Idempotency / duplicate-call protection** — retries don't cause duplicate side effects (e.g. duplicate emails generated by a retried LLM call).
- [ ] **Logging excludes sensitive payloads** — full prompts/responses aren't logged at INFO in production if they contain PII; consider redaction or DEBUG-only logging.
- [ ] **Error handling distinguishes failure types** — auth errors, rate limits, content-filter rejections, and network errors are caught and handled differently, not swallowed into a generic `Exception`.
- [ ] **Unit tests mock the chat client** — tests don't make real network calls; a fake/mock `ChatClient` or `ChatModel` is used, keeping tests fast and deterministic.
- [ ] **Observability is wired in** — metrics (latency, token usage, error rate) and tracing spans exist around LLM calls, ideally tagged by model/prompt name.

---

## 3. Pre-defined Prompts

- [ ] **Prompts are externalized from Java code** — stored as templates (resource files, `PromptTemplate` classes, or a prompts directory), not embedded as string concatenation inside business logic.
- [ ] **Prompt templates use parameterization**, not raw string interpolation of user input directly into the prompt (reduces prompt-injection risk and improves readability).
- [ ] **System prompts are centralized and versioned** — a single source of truth per use case, not duplicated/copy-pasted across services.
- [ ] **Prompt versioning strategy exists** — changes to prompts are tracked (git history is fine, but naming/versioning conventions should be consistent, e.g. `summarize_v2.prompt`).
- [ ] **User input is clearly delimited from instructions** in the template (e.g. using tags, JSON structure, or clear boundaries) to reduce prompt-injection risk.
- [ ] **No secrets or internal system details are leaked into prompts** sent to third-party LLM providers.
- [ ] **Prompts have accompanying tests or evals** — at minimum, example inputs/outputs are documented so regressions in prompt behavior are catchable.
- [ ] **Locale/language handling is explicit** if the app is multi-lingual — prompt templates account for it rather than assuming English.

---

## 4. Structured Input/Output Handling

- [ ] **Output schema is explicitly defined** — using Spring AI's `BeanOutputConverter`/structured output support, OpenAI function calling/JSON mode, or Gemini's structured output, rather than free-text parsing with regex.
- [ ] **DTOs/POJOs represent the expected LLM response shape**, annotated appropriately (Jackson annotations, validation constraints) and kept in a clear package (e.g. `dto.llm`).
- [ ] **Deserialization failures are handled gracefully** — malformed or partial JSON from the LLM doesn't crash the request; there's a fallback path or retry-with-correction strategy.
- [ ] **Input validation before sending to the LLM** — request DTOs are validated (`@Valid`, Bean Validation) before being formatted into a prompt, preventing garbage-in/garbage-out.
- [ ] **Output validation after receiving from the LLM** — response DTOs are validated against business rules (e.g. required fields present, enums within allowed values) before being used downstream.
- [ ] **Strict typing over `Map<String, Object>`** — structured responses are mapped into typed classes rather than passed around as raw maps/JSON nodes through the app.
- [ ] **Handles non-conforming responses** — if the model returns extra prose around JSON, ignores instructions, or returns an empty result, there's defensive parsing (e.g. strip code fences, extract JSON substring) rather than assuming perfect compliance.
- [ ] **Function/tool calling (if used) is scoped and validated** — tool definitions have clear schemas, and tool execution validates arguments before running (never blindly `eval`/reflect based on LLM output).
- [ ] **Sensitive fields are excluded from LLM I/O** — DTOs sent to/from the LLM don't carry internal IDs, credentials, or unrelated PII beyond what's needed.

---

## 5. General Cross-Cutting Concerns

- [ ] **Rate limiting on your own API** — endpoints that trigger LLM calls have their own throttling to control cost and abuse.
- [ ] **Caching considered** for repeatable/expensive prompts (e.g. Spring Cache) where responses can be safely reused.
- [ ] **Configuration documented** — README or config docs explain required env vars, model choices, and how to swap providers (OpenAI ↔ Gemini) if the abstraction supports it.
- [ ] **No provider lock-in leakage** — if multi-provider support is a goal, provider-specific types don't leak past the service layer into controllers/domain code.
- [ ] **Compliance/data handling** — confirm whether prompts/responses containing user data are permitted to leave the system per data governance policy, and whether provider data-retention settings (e.g. zero-retention APIs) are used where required.

---

### How to Use This Checklist
1. Walk each section against the PR/codebase under review.
2. For unchecked items, leave a review comment referencing the specific section (e.g. "Section 3: prompt is inline in `ReportService.java` line 42 — should be externalized").
3. Treat Sections 1–2 as blocking for production readiness; Sections 3–4 as high priority; Section 5 as recommended hardening.
